# 特定の進捗が動いたら通知がどこかに来る仕組み

仕様・設計・作業ルールは [`docs/CP進捗通知_システム仕様書.md`](docs/CP進捗通知_システム仕様書.md)（**唯一の根拠。**GAS 版は11章）/ [`docs/design/`](docs/design/) / [`rules/`](rules/) / [`CLAUDE.md`](CLAUDE.md)。

## 使い方

### 1. 起動方法
自動運転を開始したいときは、`setup.gs` 内の `createTriggers()` を実行して自動運転に乗せます。  
登録後、`showTriggers()` を実行することで、以下の4つのトリガーが正しく常時監視（登録）されているか確認できます。

#### 「常時監視」の正確な意味
プロセスが動き続けているのではなく、**決まった間隔で起動して数秒で終わる**を繰り返します。  
`showTriggers()` は「トリガーが正しく登録されていること」を確認するものであり、常時動作し続けているプロセス自体を監視しているわけではありません。

---

### 2. 常時監視トリガー一覧

| 関数 | 間隔 | 1回の中身 |
| :--- | :--- | :--- |
| `runProgressFlow` | 5分 | 要件2/3。進捗履歴の追加を拾う |
| `runCareerStatus` | 15分 | 要件1。求職者229項目の変化を拾う |
| `runCareerAction` | 15分 | 要件4。対応履歴の登録・更新・完了を拾ってメール |
| `runDailySummary` | 毎日7時 | 前日ぶんの集計を `ops` チャンネルへ |

---

### 3. `showTriggers()` で確認できるチェック項目

さらに以下の状態も `showTriggers()` で確認できます。

- **`duplicated` が空**：同じ関数が2本回っていないか（2本あると流量が倍になります）
- **`unmanaged` が空**：画面から手で足したトリガーが無いか

---

### 4. 実行の仕様・制限事項

- **排他制御（`LockService`）**  
  2本が同時に走ることはありません。`LockService` で排他制御しており、前の実行が終わっていなければ後発はすぐ抜けます（ログに `lock_busy` が出力されます）。
- **リクエスト流量・予算**  
  合計流量も **60 req/分** の設計上限を超えません。要件4が加わって **1日あたり約 1,150 リクエスト**、想定予算 5,000 の **23% 程度** となります。
- **反映時間差**  
  時間差は **10分程度** は覚悟してください。

---

### 5. 停止方法

止めたいときは `setup.gs` 内の **`deleteTriggers()`** を実行します。



## 共通制約

1. **CP API は 1分間に 240 リクエストを超えない。**全 HTTP 呼び出しが単一のトークンバケットを通る。
   （`rules/20-rate-limit.md`。これが最重要制約）
2. **CP に書き戻さない。**読み取り専用。
3. **秘密情報を `gas/src/` に置かない。**API キーと Slack Webhook URL は
   スクリプトプロパティに手で設定する（`rules/40-secrets-and-security.md`）。
4. **Apps Script のエディタで直接編集しない。**`clasp push` が唯一の反映経路。
5. 個人情報をログに出さない。項目 ID とリソース ID のみ。
