# 02. ウォッチャー個別設計

前提として **Webhook は存在せず、全要件がポーリングになる**。
どの通知にもポーリング間隔ぶんの遅延が必ず乗る。リアルタイム通知は原理的に不可能。

各要件の遅延と流量の対応は `docs/design/03-rate-budget.md` にまとめてある。

---

## 要件1 — `career_status` ウォッチャー

> 特定の求職者の「項目（デフォルト項目およびオリつくの項目）」のステータスが
> 特定の値に変わったら Slack に通知する

### 実現可否 — ✅ 完全に実現可能（V-1 で確定）

- **デフォルト項目: 実現可能。**
- **オリつく項目: 実現可能。**`GET /v1/ext2/schema/career` に現れることを実測で確認した。
  対象のオリつく項目は **`CAREER#48002`（ラベル「国籍（氏名・生年月日）」、text型）**。
  select・検索条件・ソートキーのすべてで使えることを確認済み
  （`07-verification-results.md` 1章）。

オリつく項目の itemId は **`{PREFIX}#{数値}`** という命名規則（標準項目は英字の記号名）。
`^[A-Z_]+#\d+$` で機械的に判別できるので、
起動時に schema を走査して「オリつく項目の一覧」をログに出す。
新しいオリつく項目が追加されたときに気づける。

### 検知方式

```
1. career/search
     condition: CAREER#UPDATE_DATE GE <カーソル>
                (+ 監視対象を絞る条件があれば AND)
     sort:      CAREER#UPDATE_DATE asc
     limit:     100
   → 変化した求職者の ID 一覧（1〜数リクエスト）

2. 各 ID について career/select
     itemIds: 監視対象項目 + CAREER#CAREER_ID + CAREER#LASTNAME + CAREER#FIRSTNAME
   → 現在値

3. snapshots の前回値と比較
     ルールの from/to にマッチした項目だけを通知イベントにする

4. snapshots を更新し、カーソルを前進
```

`CAREER#UPDATE_DATE` は datetime・読み取り専用で、`GE` が使える（原典確認済み）。

### 「特定の求職者」の絞り込み

`career` は関連リソースを持たないため、絞り込みは `CAREER#*` の条件だけで書く。
YAML の `target.condition` を CP の検索条件としてそのまま渡す。

**PoC の対象は式波アスカ（求職者ID 18）のみ**（B-1 の回答）。
`CAREER#CAREER_ID EQ 18` で絞る。`UPDATE_DATE GE` との複合条件が動くことは実測済み。

対象を広げるときは YAML の `target.condition` を書き換えるだけでよい
（担当チーム・登録ステータス・ランク等の条件に差し替え可能）。
**絞り込まないと全社の求職者更新を拾う**ので、本番展開時は必ず条件を入れる。

### 「変わった」の判定 — 値を限定せず全変化を通知する

B-3 の回答により、**「特定の値になったら」ではなく「ステータスが変わったら」**が要件。
遷移先の値を限定せず、監視対象項目の値が前回と変われば通知する。

**スナップショット比較が必須。** 検索条件だけでは「今その値である」しか分からず、
「変わった」は判定できない。

ルールの記述:

```yaml
watchers:
  career_status:
    enabled: true
    interval_minutes: 15
    priority: 2
    budget_per_cycle: 60
    overlap_seconds: 60          # datetime は秒精度で検索できる（実測）
    target:
      condition:
        compoundType: and
        items:
          - itemId: "CAREER#CAREER_ID"
            searchType: "EQ"
            value: "18"          # 式波アスカ
    watched_items:
      # 値の変化を検知する項目。値は限定しない（変わったら通知）
      - item_id: "CAREER#48002"          # オリつく項目「国籍（氏名・生年月日）」
        label_override: "国籍"
      - item_id: "CAREER#REGSTATUS_ID"   # 登録ステータス (MSTREGSTATUS)
      - item_id: "CAREER#CNSLSTATUS_ID"  # 面談ステータス (MSTCNSLSTATUS)
      - item_id: "CAREER#WKSTATUS_ID"    # 現在の状況 (MSTWKSTATUS)
      - item_id: "CAREER#RANK_ID"        # ランク (MSTCONRANK)
      - item_id: "CAREER#MYPAGE_STATUS"  # マイページステータス (MSTMYPAGECHK)
      - item_id: "CAREER#CHARGE_ID"      # 担当者 (MSTUSER)
      - item_id: "CAREER#CHARGETEAM_ID"  # 担当チーム (MSTTEAM)
    notify:
      channel: "#recruit-status"
      template: "career_item_changed"
```

判定ロジック:

- `watched_items` の各項目について、前回値と現在値を比較する。
- 異なれば通知。**遷移先の値による絞り込みはしない。**
- 前回値が snapshots にない求職者（初めて見た）は通知しない。
  既存レコードの一斉通知を避けるため（ブートストラップと同じ理由）。
- 通知本文には**変化前後の値をマスタでラベルに変換して**載せる
  （例: 面談ステータス `1` → `3` を「未対応 → 面談待ち」と表示）。
- 変化前後を表示するため、`watched_items` の項目は `snapshots.value_raw` に生値を保存する。
  この YAML に列挙された項目のみが対象（`rules/40-secrets-and-security.md`）。

将来「特定の値になったときだけ通知したい」という要望が出たら、
`watched_items` に任意の `to` / `from` フィルタを足せる構造にしておく。
既定はフィルタなし（全変化を通知）。

### 遅延と流量

| | |
|---|---|
| 間隔 | 15分（＝最大遅延15分 + 処理時間） |
| 1サイクル | 検索1〜2 + 変化した求職者数ぶんの select |
| 想定 | 求職者更新 200件/日 → 1サイクル約2件 → 約4リクエスト |

更新が集中する時間帯（一括インポート等）では変化件数が跳ねる。
予算 60 で中断し、次サイクルに持ち越す。**このとき通知は遅れるが落ちない。**

### 未確定事項

**V-1 の実施により、要件1の未確定事項はすべて解消した。**
オリつく項目の schema への出現・命名規則・検索/取得での利用可否はすべて確認済み
（`07-verification-results.md` 1章）。代替案 A〜D は不要になったため削除した。

残る確認事項は業務側への一点のみ:

- 監視対象の項目リスト（上記 `watched_items`）がこれで過不足ないか。
  現状はデフォルトのステータス系7項目 + オリつく項目「国籍」を挙げている。
  「国籍」以外のオリつく項目はこのテナントに存在しない（schema 全走査で確認済み）。

## 要件2 / 要件3 — `progress_flow` ウォッチャー

> 要件2: 求職者の進捗を、はじめから内定までのフロー全体について、フローが進行するごとに Slack に通知
>
> 要件3: 「求人紹介OK」ボタン → 小画面の「新規登録」ボタン → 新規登録された時に Slack に通知

### 業務上の意味（ヒアリング結果）

> 「求人紹介OK」は、求職者を弊社の担当者が面接し、**求人企業へ紹介してもいい人材だと判断された場合**に
> クリックされる。そうすると該当求職者は次の段階へ進み、
> **「応募OK（求人照会）」「応募NG（求人照会）」「再面談（社内確認中へ）」の3つのボタンが現れる。**

実測（V-2）と合わせると、判明しているフローは次のとおり。

```
                    [求人紹介OK]
  社内確認中(16) ──────────────────→ 応募意思確認中(求人)(11)
        ↑                                    │
        │                                    ├─[応募OK（求人照会）]──→ ?
        │                                    ├─[応募NG（求人照会）]──→ ?
        └────[再面談（社内確認中へ）]────────┘
```

**このフローは後戻りする。**「再面談」で `応募意思確認中(求人)(11)` から
`社内確認中(16)` へ戻る経路がある。

設計上の意味:

- 後戻りも**進捗履歴の追加**として記録されるはず（CP は履歴を残す設計）。
  そうであれば `INSERT_DATE GE` で前進と同じように検知できる。
  ただし「同じステータスに2回到達する」ことになるので、
  **冪等キーに枝番（`PROGRESS_ID_SUB`）を含める**必要がある。
  ステータス値だけで冪等キーを作ると、戻ってから再び進んだときに通知が消える。
- 「進捗履歴が削除されて巻き戻る」場合は検知できない（後述「拾えないもの」）。
  再面談が**履歴の追加**なのか**削除**なのかは未確認。追加である可能性が高いが、
  実装後に1度確認する（`06-open-questions.md` B-14）。

要件3は「新しい何かが登録される」のではなく、**進捗が次のステータスへ遷移するイベント**。
依頼者の言葉でも「新規登録ボタンを押して**次の進捗に移った時点**で通知が欲しい」とされている。

### ✅ 統合確定（V-2 で実測）

**「求人紹介OK → 新規登録」は進捗ステータスの遷移だった。**
2026-08-05 16:28 の実操作で確定（`07-verification-results.md` 12章）。

| 変化したもの | 内容 |
|---|---|
| `progress_history` | **`21_2` が1件追加されただけ** |
| `progress` `21` | `STATUS_ID` が `'16'`（社内確認中） → **`'11'`（応募意思確認中(求人)）** |
| その他の全リソース | **一切変化なし**（求職者の232項目も含めて） |

**要件3 は要件2 と完全に同一のデータソース。1つのウォッチャーで両方を扱う。**
新しいリソースを見に行く必要はない。

`PROGRESS#INTRODUCTION_DATE`（紹介日）は `None` のままだった。
当初これを要件3の判定条件の候補としていたが、**使えない。**

### 検知方式（統合版）

```
1. progress_history/search
     condition: PROGRESS_HISTORY#INSERT_DATE GE <カーソル>
     sort:      PROGRESS_HISTORY#INSERT_DATE asc
     limit:     100
   → 新しく作られた進捗履歴の ID 一覧（形式: "{progressId}_{枝番}"）

2. ID を文字列分解して progressId と 枝番 を取り出す（API 呼び出し不要）

3. 枝番が最小値     → 要件3 の候補イベント（進捗の新規作成）
   それ以外        → 要件2 のイベント（ステータス遷移）

   ※ `career_action` の `HISTSEQ` は 0 始まりであることが実測で判明している。
     `progress_history` の枝番が 0 始まりか 1 始まりかは V-2 の差分で確定する
     （既存25件の ID を `tools/verify/out/snapshot_before.json` に記録済み）。
     どちらでも動くよう、進捗IDごとの最小枝番を基準に判定する。

4. progress_history/select/{id}
     itemIds: PROGRESS_HISTORY#PROGRESS_STATUS_ID,
              PROGRESS_HISTORY#PROGRESS_DATE,
              PROGRESS_HISTORY#CAREER_CHARGE_ID,
              PROGRESS_HISTORY#ORDER_CHARGE_ID
   → 遷移先ステータス

5. progress/select/{progressId}
     itemIds: PROGRESS#CAREER_ID, PROGRESS#ORDER_ID, PROGRESS#STATUS_ID
   → 誰の・どの求人か

6. resolver で求職者名・求人名・企業名を解決（キャッシュヒット時は0リクエスト）

7. マスタでステータスコードをラベルに変換して Slack へ
```

**`progress_history` の変更検知に `INSERT_DATE` を使う理由**: ステータス遷移は
進捗履歴の**追加**として記録される（仕様書「ステータスの変更などは進捗履歴API経由で実施する」）。
よって「フローが進行した」＝「進捗履歴が1行増えた」であり、`INSERT_DATE GE` で漏れなく拾える。

`PROGRESS#UPDATE_DATE`（進捗本体の更新日）を見る方式もあるが、
備考や辞退理由の編集でも動くため、フロー進行の検知には過剰。
ただし**削除・巻き戻し**の検知には進捗本体を見る必要がある（下記「拾えないもの」）。

### 「はじめから内定まで」のフロー定義

進捗ステータスは `MST_PROGRESS_STATUS` マスタで定義され、**テナントごとに異なる**。
V-4 で実データを取得済み（**18件**、`07-verification-results.md` 7章）。

```
社内確認中(16) → 説明会(25) → 応募意思確認中(求人)(11) → 書類提出待ち(12)
→ 書類結果待ち(1) → 面接設定中(2) → 面接結果待ち(3) → 【内定(21)】
→ 入社意思確認中(内定)(4) → 成約処理中(5) → 入社確認待ち(6) → 請求処理中(14) → 完了(10)

異常系: 企業へNG連絡中(8) / 求職者へNG連絡中(7) / NG終了(17) / 辞退終了(9) / 削除終了(13)
```

上記の並びはマスタ API が返した順序であり、**業務上の遷移順であるという保証はない**。
CP の「進捗ステータス設定」に定義された遷移グラフは API から取得できない
（仕様書に「決められた遷移先ステータス以外は登録時にエラー」とあるので定義自体は存在する）。

**正確な順序は業務側への確認事項として残っている**（`06-open-questions.md` B-4）。
ただし下記モードA で開始する設計のため、**順序が未確定でも実装を進められる。**

設計としては次の2モードを用意する。

```yaml
watchers:
  progress_flow:
    enabled: true
    interval_minutes: 5
    priority: 1
    budget_per_cycle: 60
    overlap_seconds: 60          # datetime は秒精度で検索できる（実測）

    # モードA: 全遷移を通知（既定。フロー定義が未確定でも動く）
    notify_all_transitions: true
    # モードB: 特定のステータスへの遷移だけ通知（モードAが false のとき有効）
    watched_statuses: []

    notify:
      channel: "#progress-flow"
      template: "progress_transition"

    # 要件3: 特定の遷移だけ別チャンネル・別文面にする
    special_transitions:
      - name: "求人紹介OK"
        to_status: "11"          # 応募意思確認中(求人)。V-2 で実測確定
        from_status: "16"        # 社内確認中（省略可。指定すると誤検知が減る）
        notify:
          channel: "#job-intro"
          template: "job_intro_ok"
```

**モードA で開始することを推奨する。** マスタの返却順が業務フロー順ではないことが
V-2 で実証された（実際の遷移 `16 → 11` はマスタ順 `16 → 25 → 11` を飛ばしている）。
フロー定義を推測で埋めると通知漏れになる。まず全遷移を流し、実データを見てから絞る。

要件3は「モードAの全遷移通知」の上に**特定の遷移だけ文面とチャンネルを変える**形で乗せる。
要件2と要件3で別々にAPIを叩くことはしない。

### 拾えないもの

| 事象 | 拾えるか | 理由 |
|---|---|---|
| ステータスの前進 | ○ | 進捗履歴の追加として記録される（V-2 で実測） |
| 進捗の新規作成 | ○ | 枝番1の進捗履歴（実測） |
| **「求人紹介OK」（要件3）** | ○ | `PROGRESS_STATUS_ID = '11'` への遷移（実測） |
| **後戻りの遷移**（再面談 → 社内確認中） | ○（見込み） | 履歴の追加なら拾える。**要確認**（`06-open-questions.md` B-14） |
| 進捗履歴の**編集**（日付の直し等） | △ | `PROGRESS_HISTORY#UPDATE_DATE` を別途見れば可能。既定では見ない |
| 進捗履歴の**削除** | **×** | 削除は検索に現れない。検知するには全進捗の現在ステータスを定期照合する必要があり、コストが見合わない |
| 進捗そのものの削除 | **×** | 同上 |

削除・巻き戻しの通知が必要なら、別途「日次で全進捗のステータスを棚卸しする低頻度ウォッチャー」
を足す設計になる。要件に含まれていないため今回は作らない。**この非対応は明示的な判断。**

### 遅延と流量

| | |
|---|---|
| 間隔 | 5分（＝最大遅延5分 + 処理時間） |
| 1サイクル | 検索1 + 遷移件数 × (1 履歴select + 1 進捗select + 名前解決0〜2) |
| 想定 | 遷移 100件/日 → 1サイクル約0.35件 → 平均 約2リクエスト |

進捗の遷移は営業時間に集中する。日中の実効間隔は 5 分を維持できる見込み。

### 冪等キーの注意（後戻りがあるため）

フローが後戻りしうる（`再面談` で `11` → `16` に戻る）。
**冪等キーに `PROGRESS_ID_SUB`（枝番）を必ず含める。**

```
(watcher_id, resource_id="21_2", event_type="status_changed", payload_hash)
```

`resource_id` が進捗履歴IDそのもの（枝番を含む）なので、これで足りる。
`progressId + ステータス値` で冪等キーを作ると、
「16 → 11 → 16 → 11」と往復したときに2回目以降の通知が消える。

### 代替案は不要になった

V-2 の結果、要件3 は進捗履歴の追加であることが確定した。
検討していた代替案（求職者候補の監視／対応履歴への相乗り／運用カバー／スコープアウト）は
すべて不要。記録として残す必要もないため削除した。

## 要件4 — `career_action_new` / `career_action_diff` ウォッチャー

> 求職者画面の「対応履歴」タブに「新規対応」が登録された時・更新された時・対応完了した時、
> その求職者の「担当者」にメールで通知

### 難所

**`career_action` に `INSERT_DATE` も `UPDATE_DATE` も存在しない**（原典確認済み）。
持っている日付は `ACTION_DATE`(date) / `COMPLETE_DATE`(date) / `NEXTACTION_DATE`(datetime) の3つで、
いずれも**ユーザが入力した業務上の日付であり、レコードの変更時刻ではない**。

つまり「いつ変更されたか」を CP に問い合わせる手段が直接的には存在しない。

### 宛先 — ✅ 確定（B-9 の回答）

`CAREER#CHARGE_EMAIL`（求職者の担当者メールアドレス）。対応履歴側の
`CAREER_ACTION#ACTIONCHARGE_ID`（対応の担当）**ではない**。

**V-3a で確認済み**: `career_action/select` の `itemIds` に `CAREER#*` を混ぜられる。
**1リクエストで対応履歴の内容・求職者名・宛先メールが同時に取れる。**
`career/select` は不要。

担当者変更直後に旧担当へ送るのを避けるため、`CHARGE_EMAIL` はキャッシュせず
毎回 `career_action/select` で取り直す（同一リクエストなので追加コストはゼロ）。

### ⚠️ 宛先は空になりうる（実測）

xlsx では「必須●」だが、**検証テナントでは 18人中13人が空**だった
（`07-verification-results.md` 9章）。`CHARGE_ID` が `0` または `None` の求職者。

したがって次の処理が**必須**（仮定ではなく実際に起きる）:

- 宛先が空・不正なら**黙ってスキップしない**。フォールバック宛先（管理者）へ
  「宛先不明で通知できなかった」旨を送る。
- `CHARGE_ID = 0` と `CHARGE_ID = None` の2種類の「未設定」がある点に注意。
  どちらも「担当者なし」として扱う。
- 未設定時の送り先ポリシー（管理者へ / 通知しない / 対応履歴側の担当者へ）は
  業務側の確認待ち（`06-open-questions.md` B-10）。

### ❌ 戦略A は不成立（V-3c で確定）— 記録として残す

`career_action/search` は**関連リソース＝求職者**であり、仕様書「関連リソース」節に
「検索のエンドポイントでは、関連するリソースを使用した検索が可能です」とある。

```
career_action/search
  condition: CAREER#UPDATE_DATE GE <カーソル>
  sort:      CAREER_ACTION#HISTSEQ asc
  limit:     100
```

これが通れば、`career_action` 自身にタイムスタンプがない問題が消える。
1サイクル数リクエストで新規・更新・完了のすべてを検知できる。

**成立条件は2つ。**

| 検証 | 内容 | 結果 |
|---|---|---|
| V-3a/b | 関連リソースの項目ID（`CAREER#*`）を `career_action` の条件・取得項目に書けるか | ✅ **成立**（実測済み） |
| V-3c | **対応履歴を追加・編集したときに `CAREER#UPDATE_DATE` が更新されるか** | ⏸ **画面操作待ち** |

**V-3c の結果（2026-08-05 実測）: 動かなかった。**
アスカに対して 16:12 新規登録 / 16:13 内容更新 / 16:14 完了日入力 を行っても、
`career 18` の232項目は**一切変化しなかった**（`CAREER#UPDATE_DATE` は `15:20:48` のまま）。

**→ 戦略A は使えない。以下の戦略Bで確定。**

なお V-3a/V-3b（関連リソースの項目を取得・検索条件に使えるか）は成立しているので、
**宛先取得の 1リクエスト化という利点だけは残る。**

---

### ✅ 戦略B（確定）— ID集合の差分 + 日付窓のハッシュ比較

検知の性質が違う3つのイベントを、**それぞれ最も安いやり方で**取る。
`career_action` の ID が `{careerId}_{HISTSEQ}` 形式で、
**検索が ID 集合を返す**ことを最大限に利用する。

| イベント | 検知方法 | 取りこぼし | コスト |
|---|---|---|---|
| **新規登録** | 全ID走査。ID集合に現れた新しい ID | **なし** | `ceil(総件数/100)` req |
| **対応完了** | `COMPLETE_DATE ENTERED` の ID 集合に新しく入った ID | **なし** | `ceil(完了件数/100)` req |
| **内容更新** | 日付窓で候補を絞り `select` してハッシュ比較 | **窓外の編集は取りこぼす** | 窓内件数ぶんの `select` |

新規と完了は**日付に一切依存しない**ので取りこぼしがない。
これは当初の設計（日付窓で新規も拾う）より明確に良い。**内容更新だけが窓に依存する。**

#### なぜ「更新」だけコストが高いのか

新規・完了は**検索が返す ID 集合だけで判定できる**（`select` 不要）。
一方「内容が変わった」は、`career_action` に `UPDATE_DATE` が無い以上、
**実際に中身を取ってこないと分からない**。

| イベント | 判定に必要なもの | 1サイクルのリクエスト |
|---|---|---|
| 新規登録 | ID 集合の差分 | 検索のみ（`ceil(総件数/100)`） |
| 対応完了 | `COMPLETE_DATE ENTERED` の ID 集合の差分 | 検索のみ |
| **内容更新** | **各レコードの中身のハッシュ** | 検索 + **候補件数ぶんの `select`** |

`select` は 1リクエスト = 1レコード（仕様上そう決まっている）。
つまり更新検知のコストは**候補件数にそのまま比例する**。これが唯一の重い処理。

#### 間隔の決め方（当初の60分は根拠の弱い既定値だった）

当初 60 分としていたのは「1日150件」という**仮の想定**に基づく数字で、実データによるものではない。
`W`（走査候補件数）= 1日あたりの対応履歴件数 × 窓日数 として:

| W | 60 req/分での1周 | 15分間隔での稼働率 | 判定 |
|---:|---:|---:|---|
| 100 | 1.7分 | 11% | ✅ 余裕 |
| 300 | 5.0分 | 33% | ✅ 問題なし |
| 450 | 7.5分 | 50% | ⚠️ 他ウォッチャーを圧迫し始める |
| 900 | 15分 | 100% | ❌ 15分間隔は成立しない |

**W が 300 程度までなら 15 分間隔で回る。**
当初の想定（W=450）は 50% 稼働で危ういと判断して 60 分に落としたが、
**過度に保守的だった。既定を 15 分に変更する。**

なお `W` が予算を超えても**通知は失われない**。
予算切れで中断し、カーソルを進めずに次サイクルへ持ち越す（`01-architecture.md` 5.3）。
遅延が伸びるだけで取りこぼしにはならない。**間隔は安全側に倒す必要がない。**

`W` を決めるのは「1日あたりの新規対応履歴件数」。これが未確定
（`06-open-questions.md` C-11）。実測して窓日数と間隔を最終決定する。

#### 設計原則: 走査量を「総件数」ではなく「直近の活動量」に比例させる

対応履歴は本番で約 30,000 件ある。**この 30,000 に比例する処理を常時回してはいけない。**
15分ごとの全ID走査（300 req/サイクル）は SaaS への負荷として過大で、実運用に耐えない。

**検索は ID 集合しか返さないが、逆にそれを利用する。**
条件を変えた検索の ID 集合を比べるだけで、`select` なしに値の変化を検知できる（V-8 で実測確認）。

| 検知したいもの | `select` が要るか | 手段 |
|---|---|---|
| 新規登録 | 不要 | 窓の ID 集合の差分 |
| 対応完了 | 不要 | `COMPLETE_DATE ENTERED` の ID 集合の差分 |
| 対応日・完了日・次回日の変更 | 不要 | 日付を `EQ` でバケット化した ID 集合の差分 |
| アクション種別・担当の変更 | 不要 | `ACTION_ID` / `ACTIONCHARGE_ID` を `EQ` でバケット化 |
| **本文（メモ・テキスト）の変更** | **必須** | `select` してハッシュ比較 |

**`select` が避けられないのは本文の変更検知だけ。** これは API の構造上の制約
（`career_action` に `UPDATE_DATE` が無く、検索が値を返さない）で回避できない。

#### 母集団を絞る — 通知しないレコードは走査しない

担当者が未設定の求職者には通知しない（B-10）。**それなら走査する必要もない。**

```
condition に AND で追加:
  CAREER#CHARGE_ID  ENTERED    ← 関連リソース条件。V-8 で動作確認済み
```

検証テナントでは求職者18人中5人（28%）しか担当者が設定されていなかった。
本番でも同程度なら、**これだけで走査量が 1/3 になる。**

必要なら `CAREER#REGSTATUS_ID` で抹消済みの求職者も除外できる（動作確認済み）。

**注意**: `CAREER#CHARGE_EMAIL` は**検索条件に使えない**（400 `itemIdが定義されていません`）。
取得はできる。絞り込みには `CAREER#CHARGE_ID ENTERED` を使う。

#### 3つのウォッチャーの役割分担

**窓の幅を用途ごとに変える。ID 集合の比較は安いので窓を広く、`select` は高いので窓を狭く。**

| ウォッチャー | 間隔 | 窓 | 方式 | 1サイクル |
|---|---|---|---|---|
| **`career_action_sweep`** | 15分 | **30日** | ID集合の差分（検索のみ） | 約5 req |
| **`career_action_digest`** | 15分 | **3日** | ハッシュ比較（`select`） | W req |
| **`career_action_reconcile`** | **日次** | — | 全ID走査（検索のみ） | 300 req |

窓は `ACTION_DATE` / `COMPLETE_DATE` / `NEXTACTION_DATE` の **OR 和集合**なので、
通常の操作はすべて 30日窓に入る。

- 新規登録 → `ACTION_DATE` が当日前後 → 窓内 ✓
- 対応完了 → `COMPLETE_DATE` に当日が入る → 窓内 ✓
- 内容更新 → 元々窓内にあるレコード ✓

窓から漏れるのは「3つの日付をすべて30日以上前にした」「日付を1つも入れない」という
例外だけ。これを**日次**の全ID走査で回収する。安全網に15分の即時性は要らない。

#### 【確定スコープ】トリガーは日付3項目のみ

業務側の決定（2026-08-05）:

> `ACTION_DATE` / `COMPLETE_DATE` / `NEXTACTION_DATE` が変化したときだけ通知が来ればよい。
> 本文の変更を見る更新通知は捨ててよい。安全網の `career_action_reconcile` も要らない。
> 日付の変更でトリガーし、**アクション種別やメモ本文を担当者メールに通知**すればよい。

これにより3イベントが1つの仕組みに収まる。

| 要件の文言 | 実装上の定義 |
|---|---|
| 新規対応が**登録された時** | 窓の ID 集合に新しい ID が現れた |
| **更新された時** | 3つの日付項目のいずれかが変化した |
| **対応完了した時** | `COMPLETE_DATE` が null → 値 に変化した（＝上の特殊ケース） |

**「対応完了」は「日付が変化した」の一種**なので、検知機構は1つで足りる。
通知の文面だけを出し分ける。

**ハッシュ比較・`snapshots` への本文保存・`career_action_reconcile` はすべて不要になった。**
保存するのは各レコードの日付3つだけになり、状態も軽くなる。

#### ⚠️ 正直に言うべきこと: リクエスト数はあまり減らない

スコープは減ったが、**リクエスト数は 3.7 → 2.7 req/分 程度にしか下がらない。**
理由は「日付が変わったか」を知るには結局レコードを読む必要があるため。

検索は ID 集合しか返さないので、各レコードの日付値を知る方法は2つしかない。

| 方法 | コスト | 備考 |
|---|---|---|
| **窓内の全件を `select`** | **W リクエスト**（W ≒ 36） | **こちらを採用。**日付と同時に `ACTION_ID`・`ACTIONMEMO`・宛先も取れるので、通知本文がそのまま作れる |
| 日付を `EQ` でバケット化した検索 | 30〜40リクエスト | `ACTION_DATE`・`COMPLETE_DATE` は窓日数ぶんのバケットで済むが、**`NEXTACTION_DATE` は未来方向に範囲が無制限**でバケット数が読めない。発火分は別途 `select` が必要 |

**W ≒ 36 の規模では `select` の方が安く、かつ単純。**
バケット方式が勝つのは W が 200 を超えるあたりから。
1日あたりの件数が想定より大きかった場合の逃げ道として記録しておく（`03-rate-budget.md` 4.5）。

一方で**スコープ縮小の効果は確かにある**。

- `career_action_reconcile`（全件走査 300 req）が丸ごと不要 → **−300 req/日**
- 本文ハッシュの保存・比較が不要 → 状態が軽くなり、実装とテストが単純になる
- `select` する項目が減る（リクエスト数は変わらないがレスポンスは軽い）

#### 安全網を外したことで残る穴（当初の記述は誤りだったため訂正）

当初「窓の外の対応履歴は**永久に**検知されない」と書いたが、**これは誤り。**

窓は `OR(ACTION_DATE GE 今日-N, COMPLETE_DATE GE 今日-N, NEXTACTION_DATE GE 今日-N)` なので、
**日付が最近の値に変われば、そのレコードは窓に入ってくる。**
2年前の対応履歴でも、完了日に当日が入れば `COMPLETE_DATE GE 今日-N` が真になり、
その時点で窓に現れて検知される。「窓の外にある**間は**見えない」だけで、永久ではない。

**検知されるもの**

| ケース | 理由 |
|---|---|
| 新規登録（対応日が当日前後） | 30日窓に現れる |
| 対応完了（完了日に当日が入る） | 3日窓に入る |
| 次回コンタクト日を近い日付に変更 | 3日窓に入る |
| **何年前の対応履歴でも、日付を最近の値に変更** | **窓に入ってくる** |

**本当に残る穴**

| ケース | 実害 |
|---|---|
| 日付を「古い値」から「別の古い値」に変更（例: 20日前 → 25日前） | 30日窓には居続けるが変更検知窓に入らないため気づけない。業務上ほぼ無意味な操作 |
| 3つの日付を1つも入力せず、その後も一度も入れない | そもそも通知すべき日付が存在しない |
| 日付を30日以上前の値に変更して窓から出る | 窓から消えるが、**時間経過による自然な窓落ちと区別できない**（毎日大量に発生するため信号として使えない） |

**「日付が最近の値になる」操作はすべて捕まえられる。**
通知したいのはまさにそれなので、実質的な穴はごく小さい。

必要になれば日次の全件走査（300 req/日）を後から足せる構造は残しておく。

#### 新規と更新の分類（前回の30日窓を使う）

古いレコードの日付が変更されて窓に入ってきたとき、
スナップショットに無いため**「新規登録」と誤って通知してしまう**問題がある。

前回サイクルの 30日窓の ID 集合（`S30_prev`）を使えば、**追加コストゼロで**正しく分類できる。

```
S3 の各 ID について:
    if snapshots に日付がある       → 比較して「更新」/「対応完了」
    elif id not in S30_prev         → 「新規登録」（本当に新しい）
    else                            → 「更新」（既存レコードの日付が最近の値に変わった）
```

`S30_prev` は `cursors` とは別に、ウォッチャーの状態として保持する。

#### `career_action_watch`（新規・完了・日付変更）— 15分間隔

```
A. career_action/search   ← 30日窓 かつ 担当者あり（新規検知の広い網）
     condition:
       and:
         - CAREER#CHARGE_ID  ENTERED  ''            ← 通知対象の母集団に限定
         - or:
             - CAREER_ACTION#ACTION_DATE      GE <今日 - 30日>
             - CAREER_ACTION#COMPLETE_DATE    GE <今日 - 30日>
             - CAREER_ACTION#NEXTACTION_DATE  GE <今日 - 30日> 00:00:00
     sort: [CAREER_ACTION#CAREER_ID asc, CAREER_ACTION#HISTSEQ asc]
     limit: 100（ページング）
   → ID 集合 S30    …… 約4リクエスト

B. S30 に前回なかった ID = 「新規登録」の候補

C. career_action/search   ← 3日窓（A と同じ形、窓だけ狭い）
   → ID 集合 S3     …… 約1リクエスト
                        ※ 3日は業務側の決定。設定 change_window_days で変更可能

D. (S3 ∪ 新規候補) の各 ID を career_action/select
     itemIds:
       CAREER_ACTION#ACTION_DATE          ← トリガー
       CAREER_ACTION#COMPLETE_DATE        ← トリガー
       CAREER_ACTION#NEXTACTION_DATE      ← トリガー
       CAREER_ACTION#ACTION_ID            ← 通知本文（アクション種別）
       CAREER_ACTION#ACTIONMEMO           ← 通知本文（メモ）
       CAREER_ACTION#ACTIONCHARGE_ID      ← 通知本文（対応担当）
       CAREER#LASTNAME / CAREER#FIRSTNAME ← 通知本文（求職者名）
       CAREER#CHARGE_EMAIL                ← 宛先
   → 1リクエストで判定材料・本文・宛先がすべて揃う（V-3a で実測確認済み）
                                          …… 約36リクエスト

E. snapshots の日付3項目と比較して分類
     snapshots に日付がある:
         COMPLETE_DATE が null → 値        → 「対応完了」
         それ以外で日付3項目のいずれかが変化 → 「更新」
     snapshots に無い:
         前回の S30 にも居なかった          → 「新規登録」
         前回の S30 には居た                → 「更新」（日付が最近の値に変わって窓に入った）

F. 該当分をメール送信（宛先が空ならスキップして件数を計上）

G. snapshots を日付3項目だけで更新（本文は保存しない）
```

**30日窓（A）を残す理由**: `career_action_reconcile` を廃止したので、
新規検知の網はできるだけ広くしておきたい。ID だけなら
1日40件・担当者30%で W30 ≒ 360 → **4リクエスト**にしかならない。安い保険。

**3日窓（C）に絞る理由**: `select` は 1リクエスト＝1レコードで高い。
日付変更の検知はここに限定する。

**複数キーのソートが使えることを実測済み**なので、ページングは安定する。
`HISTSEQ` は求職者ごとの連番なので単独ではグローバルに一意にならない。
必ず `CAREER_ID` との2キーで指定する。

**`HISTSEQ` は 0 始まり**（`6_0` / `18_0` を実測）。1 始まりを前提にしない。

#### 通知の文面

トリガーは日付だが、**本文にはアクション種別とメモを載せる**（業務側の指定）。
`select` で同時に取得済みなので追加コストはない。

```
件名: [CP] 式波アスカ さんの対応履歴が更新されました

求職者   : 式波 アスカ (ID 18)
対応番号 : 0
種別     : 電話                      ← ACTION_ID をマスタでラベル化
対応担当 : 【BL】矢原アトム            ← ACTIONCHARGE_ID をマスタでラベル化

変更内容 :
  完了日     : (未設定) → 2026/08/05   ← 変化した日付だけを列挙
  次回コンタクト: 2026/08/09 → 2026/08/12

内容:
  ご本人からお電話ありました。
  メールもありました。
```

「変更内容」には**変化した日付だけ**を出す。新規登録時は3つの日付の初期値を出す。

#### `career_action_diff`（内容更新）— **15分間隔**

```
1. career_action/search   ← 3つの日付窓の OR 和集合を1リクエストで
     condition:
       compoundType: or
       items:
         - CAREER_ACTION#ACTION_DATE      GE <今日 - 窓日数>
         - CAREER_ACTION#COMPLETE_DATE    GE <今日 - 窓日数>
         - CAREER_ACTION#NEXTACTION_DATE  GE <今日 - 窓日数> 00:00:00
   → 窓内の ID 一覧

2. 各 ID について career_action/select（diff_items のみ）
   → 正規化して SHA-256、snapshots と比較

3. ハッシュが変わっていたら「更新」イベント
```

**OR による3窓の和集合が1リクエストで取れることを実測済み。**
`ACTION_DATE` が未入力でも `COMPLETE_DATE` か `NEXTACTION_DATE` があれば拾える。

窓内の全件を `select` するため、**このウォッチャーだけが重い**。
予算 120 のチャンクで分割実行し、複数サイクルかけて窓を舐める
（`docs/design/01-architecture.md` 5.3）。

#### 全ID走査のコスト（本番規模に依存する判断）

`career_action_new` のコストは総件数に比例する。**本番規模の実測が必要**（`06-open-questions.md` C-10）。

| 総対応履歴件数 | 1サイクル | 15分間隔での1日 | 平均 req/分 | 判定 |
|---:|---:|---:|---:|---|
| 5,000 | 50 | 4,800 | 3.3 | ✅ 余裕 |
| 10,000 | 100 | 9,600 | 6.7 | ✅ 問題なし |
| 30,000 | 300 | 28,800 | 20 | ⚠️ 設計上限60の1/3。許容範囲 |
| 50,000 | 500 | 48,000 | 33 | ⚠️ 間隔を30分に延ばす |
| 100,000 | 1,000 | 96,000 | 67 | ❌ 設計上限を超える。方式変更が要る |

**目安: 総件数 30,000 までは全ID走査で問題ない。**
それを超えるなら次のいずれか。

1. 間隔を延ばす（15分 → 30分/60分）。遅延と引き換えにコストが半減/1/4に
2. 新規検知も日付窓方式に切り替える（取りこぼしを許容）
3. 監視対象の求職者を絞り、`CAREER#*` の条件で `career_action/search` を絞る
   （関連リソース検索が使えるので可能。V-3b で確認済み）

**3 が最も筋が良い。** 要件1と同じく監視対象を絞れば、走査対象が業務的に意味のある範囲に減る。

#### 戦略Bの既知の取りこぼし（更新検知のみ）

新規・完了は取りこぼさない。以下は**内容更新の検知に限った**制約。

1. **窓より古いレコードの編集を拾えない。**
   窓日数の既定は 3日。「対応履歴が編集されるのは登録から何日以内か」を
   業務側に確認して調整する（`06-open-questions.md` B-8）。
2. **3つの日付項目がすべて未入力のレコードは窓に入らない。**
   検証テナントでは `ACTION_DATE` 未入力は 0 件だったが、本番では要確認（B-7）。
3. **対応履歴の削除を拾えない。**削除は検索に現れない。要件に含まれないため対応しない。
   ただし**全ID走査をしているので「ID が消えた」ことは検知できる**。
   将来削除通知が必要になれば、追加コストなしで実装できる。
4. **`ACTION_DATE` を窓外の過去日に書き換えると、次サイクル以降は窓から外れる。**

なお `ACTION_DATE` は**未来日を取りうる**（実測: `2026-08-06`）。
窓は `GE <今日 − N日>` なので未来日は常に含まれる。下限だけを気にすればよい。

### 戦略C（参考・不採用）— 求職者ごとの HISTSEQ 高水位マーク

対象求職者ごとに `career_action/search(CAREER_ACTION#CAREER_ID EQ X, sort HISTSEQ desc, limit 1)`
を叩き、前回の最大 HISTSEQ と比較する。

**不採用の理由**: 求職者1人あたり1リクエスト。監視対象500人なら1サイクル500リクエスト。
全ID走査（10,000件でも100リクエスト）より明確に高い。かつ「新規」しか検知できない。

### ルールの記述

```yaml
watchers:
  career_action_watch:
    enabled: true
    interval_minutes: 15
    priority: 3
    budget_per_cycle: 120     # 超えたら中断して次サイクルへ持ち越す

    # 走査量を直接決める最重要の設定。通知しない求職者は走査もしない
    population:
      condition:
        compoundType: and
        items:
          - itemId: "CAREER#CHARGE_ID"
            searchType: "ENTERED"
            value: ""
          # 必要なら抹消済みを除外（動作確認済み）
          # - itemId: "CAREER#REGSTATUS_ID"
          #   searchType: "NOT_EQ"
          #   value: "5"

    # OR 和集合。1リクエストで取れることを実測済み
    window_items:
      - "CAREER_ACTION#ACTION_DATE"
      - "CAREER_ACTION#COMPLETE_DATE"
      - "CAREER_ACTION#NEXTACTION_DATE"
    discovery_window_days: 30   # 新規検知の網。ID だけなので広くても安い
    change_window_days: 3       # 日付変更の検知。select するのでコストに直結
                                # 業務側の決定により 3日（2.4 req/分）
                                # 参考: 7日=5.6 / 14日=11 / 30日=24 req/分

    # 変化を検知する項目。ここに無い項目が変わっても通知しない（＝本文は対象外）
    trigger_items:
      - "CAREER_ACTION#ACTION_DATE"
      - "CAREER_ACTION#COMPLETE_DATE"
      - "CAREER_ACTION#NEXTACTION_DATE"

    # 通知本文に載せる項目。トリガーではない
    body_items:
      - "CAREER_ACTION#ACTION_ID"        # アクション種別（MSTACTION でラベル化）
      - "CAREER_ACTION#ACTIONMEMO"       # メモ本文
      - "CAREER_ACTION#ACTIONCHARGE_ID"  # 対応担当（MSTUSER でラベル化）

    notify:
      # 宛先は「求職者の担当者」。対応履歴側の ACTIONCHARGE_ID ではない（B-9）
      to_item: "CAREER#CHARGE_EMAIL"
      # 宛先が空なら送らない（B-10）。件数を集計して日次で管理者に報告する
      on_missing_address: "skip"
      templates:
        created:   "action_created"
        completed: "action_completed"
        updated:   "action_updated"
```

**`career_action_sweep` / `career_action_digest` / `career_action_reconcile` の
3ウォッチャー構成は廃止し、`career_action_watch` 1本に統合した。**
トリガーが日付3項目だけになったため、検知機構を分ける理由がなくなった。

### イベントの重複

「完了日を入れて保存した」操作は、`career_action_new` の**完了**イベントと
`career_action_diff` の**更新**イベントの両方を発火させうる。

対処: `career_action_diff` は、同一 `resource_id` について
`notified` に `completed` / `created` が**同じサイクル窓内で**記録されていたら
`updated` を抑制する。抑制ルールは YAML で切り替えられるようにする
（業務側が「両方欲しい」と言う可能性がある）。

### 遅延と流量（確定）

| イベント | 遅延 | 取りこぼし |
|---|---|---|
| **新規登録** | 15分 | 3つの日付を1つも入力しない場合のみ |
| **対応完了** | 15分 | 完了日を変更検知窓の外の日付にした場合のみ |
| **更新（日付3項目の変化）** | 15分 | 「古い値 → 別の古い値」の変更のみ（業務上ほぼ無意味な操作） |
| 本文（メモ）の変更 | — | **通知しない**（業務側の決定によりスコープ外） |

**日付が最近の値になる操作はすべて検知される。**古い対応履歴でも同じ。

走査が15分に収まらない場合も**通知は失われない**。
予算切れで中断してカーソルを据え置き、次サイクルで続きを処理する。遅延が伸びるだけ。

**要件4は 約 3,940 req/日（平均 2.7 req/分）。**
システム全体で 約 5,000 req/日（平均 3.5 req/分、CP 上限 240 の 1.5%）。
内訳と、1日あたり件数による変動は `03-rate-budget.md` 4章。

### メール送信 — Google Workspace（`@mybrainlab.net`）を使う

自前の SMTP サーバは立てない。宛先も送信元も Workspace 内で完結する。

| 案 | 方式 | 必要な準備 | 評価 |
|---|---|---|---|
| **A** | **専用アカウント + アプリパスワード**<br>`smtp.gmail.com:587` (STARTTLS) | 送信用アカウント（例 `cp-notify@mybrainlab.net`）を作り、2段階認証を有効化してアプリパスワードを発行 | **PoC 推奨。**今日から動く。組織によってはアプリパスワードが管理者により禁止されている場合があるので要確認 |
| **B** | **SMTP リレー**<br>`smtp-relay.gmail.com:587` | Admin console で SMTP リレーを有効化し、**送信元サーバの固定IPを許可リストに登録** | **本番推奨。**パスワードを持たない。CP の APIキーIP制限でどのみち固定IPを用意するので相性が良い |
| **C** | **Gmail API + サービスアカウント**（ドメイン全体の委任） | GCP プロジェクト + Admin console でスコープを委任 | 最も堅牢だが PoC には重い |
| **D** | **GAS を送信専用の中継にする** | GAS で Web App を1つ公開し、Python から POST。GAS 側は `GmailApp.sendEmail` | A/B が組織ポリシーで塞がれた場合の回避策。構成要素が増えるので第一候補にはしない |

**推奨: PoC は A、本番移行時に B へ切り替える。**
送信部分は `notifiers/mail.py` に閉じており、SMTP の接続情報を差し替えるだけで A ↔ B は移行できる。

送信元アドレスは `cp-notify@mybrainlab.net`（要作成）を想定。
`From` を実在の担当者アドレスに詐称しない（SPF/DMARC に引っかかる）。

### 宛先が無い場合の扱い（B-10 の回答を反映）

**担当者にメールアドレスが設定されていない求職者は、通知メールを送らない。**

ただし**黙って捨てない**。次の2つは必ず行う。

1. 「宛先なしでスキップした」ことを構造化ログに残す（求職者IDと対応履歴ID）
2. スキップ件数を集計し、**日次で管理者に1通サマリを送る**
   （「本日 N 件の対応履歴が担当者未設定のため通知されませんでした」）

理由: 検証テナントでは 18人中13人が担当者未設定だった。
本番でも同じ割合なら**通知の大半が消えることになる**。
黙ってスキップすると「動いているのに通知が来ない」状態に気づけない。

`snapshots` は宛先の有無に関わらず更新する。
担当者が後から設定されても、過去の対応履歴を遡って通知はしない。

### その他

- 本番相当データで動かす前に、全通知をフォールバック宛先へ流すドライラン設定で確認する。
- 送信失敗は 3 回までリトライし、諦めたら `dead_letter` に落とす。自動再送はしない。
