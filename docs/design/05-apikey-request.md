# 05. APIキー作成リクエスト

CP の「マスタ管理画面 > その他設定 > APIキー管理」で作成をお願いします。
権限は `docs/APIキー作成時の操作許可リスト.pdf` の項目名に合わせて記載しています。

---

## リクエスト内容

### APIキー名

```
cp-notify-poc
```

（最大20文字・他のAPIキーと重複しない名前。上記が使えない場合は任意の名前で構いません。
実際に設定された名前をご連絡ください）

### APIキーの利用方法

**「CAREER PLUS の API で使用する」** を選択してください。
（「ACES Meet で使用する」ではありません）

### 操作許可リスト

**作成・更新・削除はすべて不要です。読み取りのみ付与してください。**
このアプリは通知専用で、CP へ一切書き戻しません。

| 対象リソース | 作成 | 読み取り | 更新 | 削除 | 用途 |
|---|:---:|:---:|:---:|:---:|---|
| 求職者 | − | **✓** | − | − | 要件1の項目監視、要件2〜4の求職者名・担当者メールアドレス取得 |
| 求職者職歴 | − | − | − | − | 不要 |
| 求職者対応履歴 | − | **✓** | − | − | 要件4 |
| 企業 | − | **✓** | − | − | 求人取得に必要（求人のエンドポイントが企業の読み取り権限を要求するため）。通知本文の企業名 |
| 企業対応履歴 | − | − | − | − | 不要 |
| 部署 | − | **✓** | − | − | 求人取得に必要（同上） |
| 求人 | − | **✓** | − | − | 要件2・3の通知本文（求人名） |
| 求職者候補 | − | **✓** | − | − | **検証用**。要件3の「新規登録」が求職者候補を作る可能性の確認（V-2）。不要と判明したら外して構いません |
| 進捗 | − | **✓** | − | − | 要件2・3。進捗と進捗履歴の両方がこの権限で動きます |
| ファイル | − | **✓** | − | − | **検証用**。V-2 の差分スキャンで対象外を確定するため。不要と判明したら外して構いません |
| マスター | − | **✓** | − | − | **必須**。コード値をラベルに変換するため。これがないと通知本文が数値の羅列になります |
| リソース定義 | − | **✓** | − | − | **必須・最優先**。オリつく項目が API に現れるかの検証（V-1）と、項目IDの実在検証に使います |
| ACES Meet（非公開） | − | − | − | − | 不要 |

**最小構成に絞る場合**: 求職者候補とファイルの読み取りを外しても要件1・2・4は動きます。
ただし V-2（要件3の実現可否判定）の精度が落ちます。**検証期間中は付与し、検証後に外す**運用を推奨します。

### IPアドレス制限

アプリを常時起動サーバで動かすため、そのサーバのグローバル IP を CIDR で指定してください。

```
（例）203.0.113.45/32
```

**サーバの IP が確定してからお知らせします。**
確定前に検証を始めたい場合は、いったん制限なし（未設定）で発行いただき、
サーバ構築後に `/32` を追加する運用でも構いません。
その場合、制限なしの期間はキーの取り扱いに特に注意します。

## 受け取り方法

APIキーは秘密情報です。以下でお願いします。

- チャットやメール本文に平文で貼らない
- パスワード管理ツール、または期限付きの共有リンクで渡す
- 受領後はリポジトリに置かず、サーバの環境変数（`CP_API_KEY`）に設定します

## 併せて確認したいこと

APIキーの発行と合わせて、CP ベンダーへ以下を確認いただけると助かります。
詳細は `docs/design/06-open-questions.md` にあります。

1. **「1分間あたり240リクエスト」は APIキー単位ですか、契約テナント単位ですか。**
   （他の連携が同じテナントで動いている場合、合算されるかどうかで設計の余裕が変わります）
2. **オリジナル項目作成機能で追加した項目は、`GET /v1/ext2/schema/{resourceCategory}` に現れますか。**
   現れる場合、項目IDの命名規則はどうなりますか。検索条件や取得項目として使えますか。
3. **求職者画面の「求人紹介OK」→「新規登録」は、内部的にどのリソースを作成しますか。**
   （進捗レコードだと推測していますが、確証がありません）
4. **求職者の子リソース（対応履歴など）を追加・更新したとき、
   `CAREER#UPDATE_DATE`（求職者の更新日）は更新されますか。**
5. Webhook / イベント通知の提供予定はありますか。
   （現状ポーリングしか手段がなく、全通知に遅延が乗ります）

1〜4 は自分たちでも実測で確認できますが（`04-verification-plan.md`）、
ベンダー回答があれば検証工数を減らせます。

## 検証環境について

可能であれば、**本番テナントとは別の検証用テナント**、
または本番テナント内の**テスト用求職者レコード（1〜2件）**をご用意ください。

理由:
- V-2（要件3の検証）で「求人紹介OK → 新規登録」を実際に操作する必要があります。
  本番の実在求職者で行うと不要な進捗レコードが残ります
- V-3c（対応履歴の更新で求職者の更新日が動くかの確認）でも、
  対応履歴の登録・編集・完了を実際に行う必要があります

検証で発生したレコードは、確認後に削除いただくか、削除方法をご教示ください。
（アプリには削除権限を付与しないため、こちらでは消せません）
