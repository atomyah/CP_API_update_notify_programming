# 03. 流量設計と予算

## 1. 制約

仕様書「概要 > 利用方法」に次の記載がある。

> 1分間あたり240リクエストを超える場合、APIサービスを停止させて頂く可能性がございます。

これは性能上の目安ではなく**サービス停止のトリガ**であり、超えると全要件が同時に死ぬ。
設計上の最重要制約として扱う。

**未確定**: 240 が「APIキー単位」か「契約テナント単位」かの記載がない。
テナント単位（他システムの連携と合算）である可能性を前提に余裕を取る（`06-open-questions.md` Q-1）。

## 2. 予算配分

| 区分 | 値 | 上限比 |
|---|---|---|
| CP の上限 | 240 req/分 | 100% |
| **平常時の設計上限** | **60 req/分** | 25% |
| バースト（トークンバケット容量） | 20 | — |
| 緊急時の最大（設定変更でのみ到達） | 120 req/分 | 50% |

75% の余裕を残す理由:

1. 240 がテナント単位なら、他の連携・別のAPIキーの消費と合算される
2. 突発的な一括更新（データ移行、一括インポート）で変化件数が跳ねる
3. リトライ（500/504）がリクエスト数を増やす
4. 「超えたら停止」の判定条件（瞬間か平均か、超過何回でか）が不明

## 3. 想定規模

| 指標 | 値 | 出典 |
|---|---:|---|
| **本番の対応履歴 総件数** | **約 30,000** | ヒアリング（2026-08-05） |
| 1日あたりの新規対応履歴件数 | **未確定** | **要実測**（`06-open-questions.md` C-11） |
| 要件1 の監視対象求職者 | 1（式波アスカ） | PoC のスコープ |
| 求職者の総数 | 未確定 | 検証テナントは 18 |
| 1日の進捗ステータス遷移件数 | 未確定 | 検証テナントの進捗履歴は 29 |

**「1日あたりの新規対応履歴件数」が唯一の未確定パラメータ**で、
これが要件4の走査窓の件数 `W` を決める。他はすべて確定しているか、流量に影響しない。

検証テナント（求職者18・進捗16・対応履歴2）は本番規模ではないため、
`v4_v7_masters_and_scale.py` を本番テナントで再実行して確定させる。

## 4. 【重要】当初 73,000 req/日 と見積もった件の撤回

先に **約73,000 req/日（51 req/分）** と見積もったが、**これは過大だった。**
2つの保守的な選択を重ねた結果であり、どちらも必須ではない。

| 過大の原因 | 内容 | 対処 |
|---|---|---|
| **① 全ID走査を15分ごとに回していた** | 3万件 = 300 req/サイクル × 96 = **28,800 req/日**。目的は「3つの日付をすべて窓外にした対応履歴」という例外を拾う安全網 | **日次に落とす（300 req/日）。** 安全網に15分の即時性は要らない |
| **② 1日あたり100件と仮定していた** | 窓内件数 W=300 と見積もり、ハッシュ用の select が **28,800 req/日** | 実際の値は未確定。3万件が数年の蓄積なら **20〜50件/日**が現実的 |
| **③ 通知対象外のレコードまで走査していた** | 担当者未設定の求職者には通知しない（B-10）のに、その対応履歴もハッシュ比較していた | **`CAREER#CHARGE_ID ENTERED` で母集団から除外。**検証テナントでは求職者の28%しか担当者が設定されていない |

**走査量が総件数（3万）に比例する設計をやめ、直近の活動量に比例する設計にする。**

### 4.1 検証で確認できたこと（V-8）

検索は ID 集合しか返さないが、**逆に言えば「条件を変えた検索の ID 集合を比べる」だけで、
`select` なしに値の変化を検知できる。**

| 確認内容 | 結果 |
|---|---|
| 関連リソース条件（`CAREER#*`）と自リソース条件の AND | ✅ 動作 |
| `CAREER#CHARGE_ID ENTERED` で担当者ありに絞る | ✅ 動作。**通知対象の母集団を直接絞れる** |
| `CAREER#REGSTATUS_ID EQ` で登録ステータスに絞る | ✅ 動作（抹消済みを除外できる） |
| `COMPLETE_DATE ENTERED / NOT_ENTERED` | ✅ 動作。完了集合を直接取れる |
| **日付を `EQ` でバケット化** | ✅ 動作。**`select` なしに各レコードの日付が分かる** |
| **`ACTION_ID` / `ACTIONCHARGE_ID` を `EQ` でバケット化** | ✅ 動作（8値 / 12値の低カーディナリティ） |
| `ACTIONMEMO LIKE` | ✅ 動作するが**ハッシュの代わりにはならない** |
| `CAREER#CHARGE_EMAIL` を検索条件に使う | ❌ **400（`itemIdが定義されていません`）。**取得はできるが検索条件には使えない |

**結論: 日付・種別・担当の変更は `select` ゼロで検知できる。
`select` が必須なのは本文（`ACTIONMEMO` / `ACTIONTEXT1,2`）の変更検知だけ。**
これは API の構造上の制約であり、回避できない。

### 4.2 確定した設計（スコープ縮小を反映）

業務側の決定（B-16）により、**要件4のトリガーは日付3項目のみ**、
**安全網の全件走査は廃止**となった。ウォッチャーは `career_action_watch` 1本。

| 処理 | 間隔 | 窓 | 方式 | 母集団 |
|---|---|---|---|---|
| 新規の検知 | 15分 | **30日** | ID集合の差分（検索のみ） | 担当者あり |
| 日付3項目の変化 + 完了の検知 | 15分 | **3日** | `select` して日付を比較 | 担当者あり |
| ~~全件照合（安全網）~~ | — | — | **廃止** | — |

### 4.3 見積り（確定値: 変更検知窓 **3日** / 1日40件・担当者設定率30%と仮定）

| 処理 | 1サイクル | 1日 |
|---|---:|---:|
| `progress_flow`（要件2+3） | 約3 | 約860 |
| `career_status`（要件1・アスカ1名） | 約2 | 約190 |
| 新規検知（30日窓・ID のみ） | 約4 | 約380 |
| 変更候補の抽出（3日窓・ID のみ） | 約1 | 約100 |
| **日付比較のための `select`（3日窓）** | **約36** | **約3,460** |
| schema / master 再取得 | 15 | 15 |
| **合計** | | **約 5,000 req/日** |

平均 **3.5 req/分**（CP 上限 240 の **1.5%**）。当初見積り（73,000）の **1/15**。

### 4.4 変更検知窓によるコスト（3日を選択した根拠）

支配的なのは `select`。`W = 1日件数 × 変更検知窓 × 担当者設定率`。

**1日40件・担当者設定率30% の場合:**

| 変更検知窓 | W | `select`/サイクル | 平均 req/分 | 合計/日 | 検知できない編集 |
|---:|---:|---:|---:|---:|---|
| **3日（採用）** | **36** | **36** | **2.4** | **約3,500** | 4日以上前の日付の書き換え |
| 7日 | 84 | 84 | 5.6 | 約9,600 | 8日以上前 |
| 14日 | 168 | 168 | 11 | 約16,200 | 15日以上前 |
| 30日 | 360 | 360 | 24 | 約34,600 | 31日以上前 |

業務側の判断により **3日** を採用（2026-08-05）。SaaS への負荷を最小に抑える方針。

**日付が最近の値に変わる操作は窓幅に関係なく検知される**（`02-watchers.md`）。
窓幅が効くのは「古い日付を別の古い日付に書き換える」ケースのみで、
業務上ほぼ発生しないと判断した。

**1日あたり件数による変動（窓3日固定）:**

| 1日件数 | W | 合計/日 | 平均 req/分 |
|---:|---:|---:|---:|
| 20 | 18 | 約3,300 | 2.3 |
| 40 | 36 | 約5,000 | 3.5 |
| 100 | 90 | 約10,200 | 7.1 |
| 200 | 180 | 約18,800 | 13.1 |

**1日200件でも 13 req/分**（CP 上限の 5.5%）。中規模バッチにはならない。

### 4.5 スコープ縮小で減ったもの・減らなかったもの

**減ったもの**

| 項目 | 効果 |
|---|---|
| 全件走査（`career_action_reconcile`）の廃止 | **−300 req/日** |
| 本文ハッシュの保存・比較 | 状態が軽くなり実装・テストが単純化。リクエスト数には影響なし |
| ウォッチャー 3本 → 1本 | 運用と可観測性が単純化 |

**減らなかったもの（正直に記録する）**

日付が変わったかを知るには、結局レコードを読む必要がある。
検索は ID 集合しか返さないため、`select` は避けられない。

代替として日付を `EQ` でバケット化する方式も検証したが、
**`NEXTACTION_DATE` が未来方向に範囲無制限**でバケット数が読めず、
W ≒ 36 の規模では `select` の方が安く単純だった。

### 4.6 それでも重いと判断する場合の選択肢

| 手段 | 効果 | 失うもの |
|---|---|---|
| 変更検知の窓を狭める（3日 → 1日） | `select` が 1/3 | 2日以上前の対応履歴の日付変更を検知しない |
| 変更検知の間隔を延ばす（15分 → 30分） | `select` が 1/2 | 更新通知が最大30分遅れる |
| 母集団をさらに絞る（登録ステータス・担当チーム等） | 絞った割合ぶん | 対象外の求職者を通知しない |
| 日付を `EQ` でバケット化する方式に切り替える | W > 200 なら有利 | 実装が複雑。`NEXTACTION_DATE` の範囲設計が要る |

**W が 200 を超えたらバケット方式への切り替えを検討する**（それ以下では `select` が優位）。

## 5. 参考: 当初の見積り（撤回済み・経緯の記録）

戦略A は V-3c で不成立が確定したため、戦略B（`02-watchers.md`）での見積り。

### 4.1 固定費（対応履歴の件数に比例する部分）

`career_action_new` の全ID走査 = `ceil(30,000 / 100)` = **300 リクエスト/サイクル**。
完了集合の走査は `COMPLETE_DATE ENTERED` の件数に比例（完了率50%なら 150）。

### 4.2 変動費（1日あたりの対応履歴件数に依存）

`career_action_diff` の走査候補件数 `W` = 1日あたり件数 × 窓日数（既定3日）。

| 1日あたり | W（3日窓） | diff の1周 | 15分間隔での1日 |
|---:|---:|---:|---:|
| 30件 | 90 | 1.5分 | 8,640 |
| 50件 | 150 | 2.5分 | 14,400 |
| 100件 | 300 | 5.0分 | 28,800 |
| 150件 | 450 | 7.5分 | 43,200 |

### 4.3 合計（1日あたり100件と仮定した場合）

| ウォッチャー | 間隔 | 1サイクル | 1日合計 |
|---|---|---:|---:|
| `progress_flow`（要件2+3） | 5分 | 約 3 | 約 860 |
| `career_status`（要件1・アスカ1名） | 15分 | 約 2 | 約 190 |
| `career_action_new`（新規・完了） | 15分 | 約 450 | 約 43,200 |
| `career_action_diff`（内容更新） | 15分 | 約 300 | 約 28,800 |
| schema / master 再取得 | 24時間 | 15 | 15 |
| **合計** | | | **約 73,000 req/日** |

平均: 73,000 ÷ 1,440分 ≒ **51 req/分**

**設計上限 60 req/分 に対して 85%。CP の上限 240 に対しては 21%。**

この見積りは **4章で撤回済み**。全ID走査を15分ごとに回し、
1日100件と仮定し、通知対象外のレコードまで走査していた結果の数字。
正しい見積りは 4.3 を参照（約 5,350 req/日）。

### レート上限の再設定

当初 90 req/分に引き上げようとしたが、**組み直した設計では 60 req/分で十分**。
1日200件の場合でも平均 13 req/分、ピークでも 60 を超えない。

**既定は 60 req/分（CP 上限 240 の 25%）に戻す。**

## 5. ピークの扱い

平均 8.5 req/分でも、ピークは平均どおりには来ない。

### 5.1 `career_action_diff` のピーク

1周 460 リクエスト。60 req/分のトークンバケットでは **約7.7分**かかる。

対処: 予算 120 のチャンクに分割し、`exhausted=True` で中断して再スケジュールする
（`01-architecture.md` 5.3）。チャンクの合間に優先度1の `progress_flow` が割り込むので、
要件2の5分間隔が守られる。

窓1周は 4 チャンク ≒ 4 サイクル。60分間隔なので、**内容更新の検知遅延は最大約60分**
（1周が60分以内に完了する限り）。

### 5.2 突発的な一括更新

データ移行や一括インポートで `CAREER#UPDATE_DATE` が数千件動く可能性がある。

対処:
- 各ウォッチャーは予算で必ず中断する。カーソルは進めないので取りこぼさない。
- ただし**通知が数千件 Slack に流れる**という別の問題が起きる。
  1サイクルの通知件数に上限（既定 50 件）を設け、超えたら
  「N件の変更が検出されました（詳細は省略）」というサマリ通知に切り替える。
  この上限は YAML で設定する。

### 5.3 ブートストラップ

初回のスナップショット構築は全件走査になる。

- 要件1: 監視対象500人 → 検索5 + select 500 ≒ 505 リクエスト
- 要件4: 窓内450件 → 検索5 + select 450 ≒ 455 リクエスト

いずれも予算に従ってチャンク実行し、複数サイクルかけて完了させる。
**ブートストラップ中は通知を出さない**（`rules/30-state-and-idempotency.md`）。

60 req/分なら合計 960 リクエストで約16分。実用上問題ない。

## 6. リクエスト数を減らす手段（実装済みとして設計に織り込むもの）

| 手段 | 効果 |
|---|---|
| 検索の `limit` は常に 100 | ページ数が最小になる |
| `select` の `itemIds` を必要最小限にする | リクエスト数は減らないがタイムアウトリスクが減る |
| 進捗履歴IDから `progressId` を文字列分解 | `progress_history/select` を挟まずに `progress/select` へ行ける場合がある |
| 対応履歴IDから `careerId` を文字列分解 | どの求職者の対応履歴かが0リクエストで分かる |
| 検索結果の ID 集合だけで新規判定 | 要件4の新規・完了検知が `select` 不要になる |
| `resolver` の名前解決キャッシュ | 進捗通知1件あたり2リクエスト削減 |
| 関連リソースの項目を同時取得（V-3a 成立時） | 要件4で `career/select` が不要になる |
| schema / master の24時間キャッシュ | 1日15リクエストに収まる |

## 7. 監視

以下を常時記録し、設計との乖離を検出する。

- 直近1分・5分・60分の実リクエスト数（設計上限 60/分の 80% を5分継続で超えたら警告）
- ウォッチャー別・エンドポイント別の累積リクエスト数
- 各サイクルの `requests_used` / `events_detected` / `events_notified` / `exhausted`
- カーソルの遅れ（現在時刻 − カーソル値）。これが単調増加していたら
  ウォッチャーが処理しきれていない

**カーソルの遅れが増え続けるのが最も危険なシグナル。**
予算不足か、変化件数の想定違いか、どちらかが起きている。
