## 2. 【最重要】日時の形式は仕様書の記載が誤り（V-6）

**リクエストとレスポンスで形式が非対称。** どちらも仕様書の記載（`yyyy/MM/dd HH:mm`）と違う。

### レスポンス（取得時の値）

| 型 | 実際の形式 | 例 | 仕様書の記載 |
|---|---|---|---|
| `datetime` | **ISO 8601・秒あり** | `2026-08-05T15:20:48` | `yyyy/MM/dd HH:mm`（誤り） |
| `date` | **ISO 8601** | `2026-08-05` | `yyyy/MM/dd`（誤り） |
| `number` | **JSON の数値**（文字列ではない） | `18` | 記載なし |

### リクエスト（検索条件の `value`）

| 型 | 受け付ける形式 | 拒否される形式 |
|---|---|---|
| `datetime` | **`YYYY/MM/DD HH:MM:SS`** または `YYYY/MM/DD` | `YYYY/MM/DD HH:MM`（**仕様書の記載そのもの**）、ISO 8601、ハイフン区切り |
| `date` | **`YYYY/MM/DD`** のみ | ISO 8601（ハイフン区切り） |

400 のメッセージが形式を明示している:
> `itemTypeがdatetimeの場合はYYYY/MM/DD形式またはYYYY/MM/DD HH:MM:SS形式で入力してください。`

**つまり「読んだ値をそのまま検索条件に渡す」ことができない。必ず変換が要る。**
`core/timefmt.py` にこの変換を集約する設計は妥当だった。

### 秒精度は実際に効く（境界テスト）

式波アスカの `UPDATE_DATE` = `2026-08-05T15:20:48` に対して:

| 条件 | 件数 | アスカを含むか |
|---|---|---|
| `GE 2026/08/05 15:20:47` | 1 | ✅ |
| `GE 2026/08/05 15:20:48` | 1 | ✅（GE なので境界を含む） |
| `GE 2026/08/05 15:20:49` | 0 | ❌ |

**秒単位で正確にフィルタされる。**

**設計への影響（重要）**: `00-findings.md` 2.6 と `rules/30-state-and-idempotency.md` の
「datetime に秒がないのでカーソルは分粒度が下限、オーバーラップ5分が必要」という前提は**誤りだった**。

- カーソルは**秒粒度**で持てる
- オーバーラップは 5分 → **60秒**に短縮してよい
- ただし**オーバーラップ自体は引き続き必要**。理由は秒精度の不足ではなく、
  「CP 側で UPDATE_DATE が確定してから検索に反映されるまでのラグ」と
  「同一秒に複数レコードが更新されうること」が残るため
- 冪等キーによる重複除去は引き続き必須

### その他のクエリ挙動

### ❌ V-3c は不成立（画面操作で確定）

**対応履歴を操作しても `CAREER#UPDATE_DATE` は動かない。**

式波アスカ（ID 18）に対して実施した操作:

| 時刻 | 操作 |
|---|---|
| 16:12 | 対応履歴を新規登録 |
| 16:13 | 内容（`ACTIONMEMO`）だけを更新 |
| 16:14 | 完了日を入力 |

結果: `career 18` の全232項目が**一切変化しなかった**。
`CAREER#UPDATE_DATE` は操作前と同じ `2026-08-05T15:20:48` のまま。

**→ 要件4の戦略A（親のタイムスタンプで変更検知）は使えない。戦略Bで確定。**

作られた対応履歴 `18_0` の中身:

| 項目 | 値 |
|---|---|
| `CAREER_ACTION#HISTSEQ` | `0`（**0 始まり**を再確認） |
| `CAREER_ACTION#ACTION_DATE` | `2026-08-06`（**当日より未来の日付**） |
| `CAREER_ACTION#COMPLETE_DATE` | `2026-08-05` |
| `CAREER_ACTION#NEXTACTION_DATE` | `2026-08-09T00:00:00` |
| `CAREER_ACTION#ACTIONCHARGE_ID` | `8`（**求職者担当の 7 とは別人**） |
| `CAREER#CHARGE_EMAIL`（関連リソース経由） | `a.yahara@mybrainlab.net` ✅ |

**重要な副産物**:

1. **`ACTION_DATE` は未来日になりうる。**日付窓を「今日 − N日 以上」で切れば
   `GE` なので未来日も入る。窓の下限だけを気にすればよい。
2. **対応の担当（`ACTIONCHARGE_ID = 8`）と求職者の担当（`CHARGE_ID = 7`）は別人になりうる。**
   B-9 の回答どおり宛先は求職者の担当（`CAREER#CHARGE_EMAIL`）を使う。
   この2つを取り違えると誤送信になる。
3. **関連リソース経由で宛先メールが実際に取れた**（V-3a の実運用での裏付け）。

## 4. アクセストークンの挙動（仕様書に記載なし）

実測で判明した、ドキュメントにない重要な挙動。

| 挙動 | 結果 |
|---|---|
| トークンエンドポイントのレスポンス | `code`/`result` の共通ラッパが**ない**。`{accessToken, refreshToken, expiresIn}` のフラットな JSON |
| `expiresIn` | 3600（仕様書どおり） |
| トークンの実体 | RS256 の JWT。`iss=careerplus.jp` / `aud=conson` / `exp` は発行から3600秒後 |
| APIキーで複数回取得 | 発行された**複数のトークンが同時に有効**（別系列として扱われる） |
| **refreshToken でリフレッシュ** | **同系列の直前のアクセストークンが即座に無効化される（猶予期間なし）** |
| 古い系列の refreshToken | 引き続き使える（系列は独立） |
| `Authorization` ヘッダ | `Bearer <token>` が正。`bearer`（小文字）は 401。`Bearer` を付けない生トークンでも通る（が仕様どおり `Bearer` を使う） |

**設計への影響**: リフレッシュは「新トークン取得 → 直ちに差し替え」を原子的に行う必要がある。
リフレッシュ後に旧トークンを使うリクエストは必ず 401 になる。
逐次実行の単一プロセス設計ならこの制約は自然に満たされるが、
**将来並行化するなら重大な制約になる**（`rules/10-cp-api.md` に記載）。

### APIキーは読み取り専用で正しく作成されている

**当初「進捗に作成権限が付いている」と判定したが、これは誤りだった。**

`POST /v1/ext2/progress/` が 403 ではなく 400 を返したことを「権限あり」と解釈したが、
対照実験の結果、**CP は「ボディ検証 → 認可」の順で処理している**ことが分かった。

| エンドポイント | ボディ | 結果 |
|---|---|---|
| `POST /v1/ext2/career_action/` | `items` の itemId のみ不正 | 403 ✅ |
| `POST /v1/ext2/wrkcareer/` | `items` の itemId のみ不正 | 403 ✅ |
| `PUT /v1/ext2/progress/21` | `items` の itemId のみ不正 | **403 ✅** |
| `PUT /v1/ext2/progress_history/21_1` | `items` の itemId のみ不正 | **403 ✅** |
| `POST /v1/ext2/career_workexperience/` | **必須パラメータ（`careerId`）が不正** | **400**（作成権限は無いのに） |
| `POST /v1/ext2/progress/` | **必須パラメータ（`progressDate`）が不正** | **400** |

対照実験の要点: `career_workexperience` は画面上も作成権限が未チェックだが、
必須パラメータを不正にすると 403 ではなく 400 が返る。
**つまり 400 は権限の有無を示していない。**

進捗系は `PUT` で 403 が返っており、権限は正しく効いている。
APIキー管理画面のスクリーンショットでも全リソースの作成・更新・削除は未チェック。

**→ APIキーの設定変更は不要。前回の依頼は取り下げる。**

検証中にデータは一切作られていない（各リソースの件数が操作前後で一致することを確認済み）。

### 新しく作られた進捗履歴 `21_2`（`21_1` との差分）

| 項目 | `21_1`（進捗の作成） | `21_2`（求人紹介OK） |

### 結論

**要件3 は「新しいリソースが作られるイベント」ではなく、
「進捗ステータスが `社内確認中(16)` から `応募意思確認中(求人)(11)` へ遷移するイベント」だった。**

**要件2 と完全に同一のデータソース（`progress_history` の追加）。
1つのウォッチャーに統合できることが確定した。**

判別条件:

```
progress_history/search  condition: PROGRESS_HISTORY#INSERT_DATE GE <カーソル>
  → 得られた ID（例 "21_2"）を文字列分解して progressId=21 / 枝番=2 を得る（API 呼び出し不要）
  → progress_history/select で PROGRESS_STATUS_ID を取得
      == '11' なら 要件3（求人紹介OK）のイベント
      それ以外   なら 要件2（通常のフロー進行）のイベント
```

実クエリの動作確認済み: `INSERT_DATE GE 2026/08/05 16:20:00` → `count=1, ids=['21_2']`。

### 後戻り（再面談）も履歴の追加（B-14 確定）

「再面談（社内確認中へ）」を押した結果（16:55:53）:

| 履歴ID | 枝番 | ステータス | INSERT_DATE | RELATED_DATE |
|---|---:|---|---|---|
| `21_1` | 1 | `16` 社内確認中 | 16:06:32 | `None` |
| `21_2` | 2 | `11` 応募意思確認中(求人) | 16:28:08 | 16:28:08 |
| **`21_3`** | **3** | **`16` 社内確認中** | **16:55:53** | `None` |

`21_2` は**削除されていない**。新しい枝番 `21_3` が追加された。
進捗本体は `STATUS_ID` が `16` に戻り、`LASTPROGRESS_ID_SUB` が `3` になった。

**→ 後戻りも `PROGRESS_HISTORY#INSERT_DATE GE` で通常の遷移と同じ経路で検知できる。**

**冪等キーに枝番が必要な理由が実証された。**
`21_1` と `21_3` は**同じステータス値 `16`**。
`progressId + ステータス値` で冪等キーを作ると `21_3` の通知が重複扱いされて消える。
`resource_id` に進捗履歴ID（`21_3`）を使えば正しく区別できる。

補足: `RELATED_DATE` は「求人紹介OK」による前進（`21_2`）にだけ入り、
作成（`21_1`）と後戻り（`21_3`）では `None` だった。
遷移の種類を示す手がかりになりうるが、判定には `PROGRESS_STATUS_ID` を使う方が確実。

### フロー順序についての補足

実際の遷移は **`社内確認中(16)` → `応募意思確認中(求人)(11)`** で、
マスタの返却順（`16 → 25(説明会) → 11 → ...`）とは**一致しない**（`説明会` を飛ばしている）。

**マスタの返却順は業務フロー順ではない**ことが実データで裏づけられた。
`02-watchers.md` の「モードA（全遷移を通知）で開始する」方針が正しい。
