## D. 設計上、意図的に対応しないと決めたこと

後から「なぜ対応していないのか」と問われたときのための記録。

| 内容 | 理由 |
|---|---|
| 進捗の**削除・巻き戻し**の通知 | 削除されたレコードは検索に現れず、検知には全進捗の定期照合が要る。要件に含まれていない（B-5 で確認中） |
| 対応履歴の**削除**の通知 | 同上 |
| **リアルタイム通知** | Webhook が存在しないため原理的に不可能。最短でポーリング間隔ぶんの遅延が乗る |
| ウォッチャーの**並行実行** | トークンバケットの競合と可観測性の悪化に見合う利得がない（`01-architecture.md` 2章） |
| **非エンジニア向けの設定 UI** | 現時点で要求がない。ただしルールの読み込みを1箇所に閉じ、将来スプレッドシート等に差し替えられる形にしてある |
| CP への**書き込み**（通知済みフラグの書き戻し等） | 権限を持たない設計にすることで事故の可能性を消す。通知済み管理は SQLite で行う |
| 走査窓より古いレコードの変更検知 | 全件走査になり流量制約に反する。窓日数は B-8 の回答で調整する |
