> 判断された場合にクリックされる。そうすると該当求職者は次の段階へ進み、

```
                    [求人紹介OK]
  社内確認中(16) ──────────────────→ 応募意思確認中(求人)(11)
        ↑                                    │
        │                                    ├─[応募OK（求人照会）]──→ ?
        │                                    ├─[応募NG（求人照会）]──→ ?
```

  `progressId + ステータス値` で作ると往復時に通知が消える

## 残っている確認事項

実装のアーキテクチャは確定しているが、設定値と運用方針が決まらない。

### 1. 本番テナントの対応履歴の総件数（C-10）

要件4の新規・完了検知は**対応履歴を全件走査**する方式（日付に依存せず取りこぼしなし）。
コストが総件数に比例する。

| 総件数 | 1サイクル | 判定 |
|---:|---:|---|
| 〜10,000 | 〜100 req | ✅ 15分間隔で余裕 |
| 〜30,000 | 〜300 req | ⚠️ 許容範囲 |
| 50,000〜 | 500 req〜 | ❌ 間隔を延ばすか監視対象を絞る |

### 2. 担当者未設定の求職者への通知先（B-10）

検証テナントでは **18人中13人**の求職者で `CAREER#CHARGE_EMAIL` が空だった
（`CHARGE_ID` が `0` または未設定）。

- (a) 管理者へフォールバック（「宛先不明」として通知）
- (b) 通知しない
- (c) 対応履歴側の担当者（`CAREER_ACTION#ACTIONCHARGE_ID`）へ送る

実測で、対応履歴の担当（`8`）と求職者の担当（`7`）が**別人になりうる**ことを確認済み。

### 3. 要件4の「内容更新」の遅延は最大1時間（B-6）

新規登録と対応完了は15分以内。内容更新だけは実際に中身を取って比較するしかなく、
コストが高いため60分間隔。許容できるか。

### 4. 通知先と実行環境（B-11 / C-1 / C-2 / C-3）

### 5. 「再面談」で進捗履歴が追加されるか削除されるか（B-14）

後戻りが**履歴の追加**なら通常のフロー進行と同じ経路で検知できる。
**削除**だと検知できない。追加である可能性が高いが未確認。

急がないが、実装前に分かっていると設計が締まる。
