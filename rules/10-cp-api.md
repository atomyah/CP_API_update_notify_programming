# ルール: CP API の扱い

## エンドポイント

- FQDN は `https://api.careerplus.jp` 固定。
- 業務リソースは `/v1/ext2/` 配下。認可のみ `/v1/auth/token`。
- 全リクエストに `Authorization: Bearer <アクセストークン>` を付ける（`/v1/auth/token` を除く）。

## 認可

- アクセストークンは 60 分有効（`expiresIn: 3600`）。RS256 の JWT。
- 取得手段は APIキー（`grantType: "api_key"`）か refreshToken（`grantType: "refresh_token"`）。
- **トークンエンドポイントのレスポンスには `code`/`result` の共通ラッパがない。**
  `{accessToken, refreshToken, expiresIn}` のフラットな JSON が返る。
  他のエンドポイントと同じパーサを使い回さないこと。
- トークンはメモリ上でキャッシュし、**有効期限の 5 分前**に再取得する。
- `401 UNAUTHORIZED` を受けたら 1 回だけトークンを再取得してリトライする。
  2 回目の 401 は設定不備として扱い、リトライループに入らない。
- ヘッダは `Authorization: Bearer <token>`。**`bearer`（小文字）は 401 になる。**

### ⚠️ リフレッシュすると旧アクセストークンが即座に死ぬ（実測。仕様書に記載なし）

`refresh_token` でトークンを取り直すと、**同じ系列の直前のアクセストークンがその瞬間に無効化される。**
猶予期間はない。リフレッシュ後に旧トークンで投げたリクエストは必ず 401 になる。

- トークンの差し替えは原子的に行う。「新トークンを取得してから差し替える」の間に
  旧トークンを使うコードパスを作らない。
- **これは将来ウォッチャーを並行実行する場合の重大な制約になる。**
  逐次実行の単一プロセス設計ならこの問題は自然に回避される。
- なお APIキーから複数回取得したトークンは別系列として扱われ、同時に有効。
  「1キー1トークン」ではない。

## 検索（`POST /v1/ext2/{resource}/search`）

- レスポンスは **ID の配列（`ids`）と総件数（`count`）のみ**。項目値は返らない。
- `limit` の最大は 100、未指定時は 20。**必ず明示的に指定する。**
- `sort` を指定しない場合、並び順は保証されない。
  ページングするときは必ず一意に定まるソートキーを指定する。
- 深いオフセットのページングはタイムアウトの可能性がある（仕様書に明記）。
  1 回の検索で辿るページ数に上限を設け、超えたら次サイクルに持ち越す。
- `value` に `null` は指定できない。未入力の判定は `NOT_ENTERED` を使い、`value` は空文字を渡す。

### 比較方法（searchType）と項目タイプの対応

`date` / `datetime` / `number` で使えるのは `GT LT GE LE EQ NOT_EQ ENTERED NOT_ENTERED`。
`LIKE` 系は使えない。`textarea` は `EQ`/`NOT_EQ`/`GT`/`LT`/`GE`/`LE` が使えない。
新しい検索条件を書くときは `docs/design/00-findings.md` の対応表を必ず確認する。

## 取得（`POST /v1/ext2/{resource}/select/{id}`）

- **1 リクエスト = 1 リソース。**N 件欲しければ N 回叩く。ここが流量の主因。
- リクエストボディの `itemIds` に必要な項目だけを列挙する。
  「とりあえず全項目」を取らない（レスポンスサイズとタイムアウトのリスク）。
- 関連リソースを持つエンドポイントでは、関連リソースの項目 ID も `itemIds` に混ぜられる
  （仕様書「リソース定義について - 関連リソース」）。**ただし実測未検証。**
  これが成立すると要件4のリクエスト数が大幅に減るため、検証結果に応じて実装を切り替える。

## 値の形式（実測。仕様書の記載は誤り）

**リクエストとレスポンスで形式が違う。読んだ値をそのまま検索条件に渡せない。**

### レスポンス（取得時の値）

| 項目タイプ | 実際の形式 | 例 |
|---|---|---|
| `text` / `selectone` / `search` | 文字列そのまま | `"米国"` |
| `textarea` | 改行が `\n` | |
| `select` | 文字列の配列 | `["8","9"]` |
| `date` | **ISO 8601** | `2026-08-05` |
| `datetime` | **ISO 8601・秒あり** | `2026-08-05T15:20:48` |
| `number` | **JSON の数値**（文字列ではない） | `18` |

### リクエスト（検索条件の `value`）

| 項目タイプ | 受け付ける形式 |
|---|---|
| `date` | **`YYYY/MM/DD`** のみ |
| `datetime` | **`YYYY/MM/DD HH:MM:SS`** または `YYYY/MM/DD`（後者は `00:00:00` 扱い） |

`YYYY/MM/DD HH:MM`（分まで・仕様書に書かれている形式）は **400 で拒否される**。
ISO 8601 やハイフン区切りもすべて 400。

**秒精度は実際に効く**（`GE ...15:20:48` と `GE ...15:20:49` で結果が変わることを実測済み）。
よってカーソルは秒粒度で持てる。ただしオーバーラップと冪等除去は引き続き必須
（`rules/30-state-and-idempotency.md`）。

形式変換は `core/timefmt.py` の 1 箇所に集約する。各所で `strftime` を書かない。

## コード値

`selectone` / `select` / `search` の値はコード値であり、そのまま通知に出すと意味が読めない。
`GET /v1/ext2/master/{codeName}` でラベルに変換してから通知本文に載せる。
参照すべきマスタ名は項目一覧の「参照マスタ」列にある（例: `MST_PROGRESS_STATUS`, `MSTUSER`）。
マスタは起動時に取得し、24時間キャッシュする。

## 項目 ID の扱い

- 項目 ID をコードに直書きしない。YAML 設定か定数モジュールに集約する。
- 起動時に `GET /v1/ext2/schema/{resourceCategory}` を取得し、
  **設定に書かれた項目 ID が実在するかを検証する。**存在しなければ起動を失敗させる。
  項目一覧 xlsx と実環境がずれている可能性があるため、実環境の schema を正とする。

## エラーコード

| コード | 扱い |
|---|---|
| 400 | リクエスト不正。リトライしない。設定不備としてログに残し、そのイベントを dead letter に落とす |
| 401 | トークン再取得して 1 回だけリトライ |
| 403 | APIキーの権限不足。リトライしない。起動時チェックで早期に検出する |
| 404 | エンドポイント誤り。リトライしない |
| 500 | 指数バックオフで最大 3 回リトライ |
| 504 | 指数バックオフで最大 3 回リトライ。リクエスト内容の見直しもログに促す |

リトライは必ずトークンバケットを消費する。バックオフ中も他ウォッチャーを止めない。
