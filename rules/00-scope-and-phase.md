## 実装するときの禁止事項

- **設計書の該当節が未確定なまま実装しない。**「とりあえず動くものを」と言われても、
  未確定である旨と決めるべき論点を返す。
- 仕様書に書かれていない挙動を勝手に足さない。足すなら仕様書を先に更新する。
- 実 API を叩くテストを CI に置かない（流量制約に反する。`rules/50-code-style.md`）。
- **疎通・動作確認をしていないのに、したかのような記述をしない。**

## 推測で埋めない

原典（`docs/` の3ファイル）に書かれていないことは、書かれていないと明記する。

- 「たぶんこうなっている」で設計を進めない。実環境で確認すべき項目として
  `docs/design/04-verification-plan.md` に追記する。
- 事前調査やこれまでの会話で述べられた内容も、原典で裏が取れていなければ「未検証」と扱う。
- 特に次の3つは実環境でしか確定しない。これらに依存する設計は必ず分岐と代替案を持つこと。
  1. オリつく項目が `GET /v1/ext2/schema/{resourceCategory}` に現れるか
  2. 「求人紹介OK → 新規登録」が CP 内部でどのリソースを作るか
  3. 関連リソースの項目 ID（`CAREER#*`）を `career_action` の検索条件・取得項目に混在できるか

## 要件が成立しないと分かったとき

黙って別の要件にすり替えない。次の順で報告する。

1. 何が成立しないか（原典のどの記述・どの項目の不在によるか）
2. 実環境で確認すれば覆る可能性があるか。あるならその検証手順
3. 代替案を複数（実現度・コスト・失うものを添えて）
4. すべて不可なら「CP ベンダーへの機能要望」または「運用でカバー」まで含めて提示

## 変更に責任を持つ範囲

設計書とルールは、決定が変わったら**その場で更新する**。
会話の中だけで決まった前提を放置しない。次のセッションに残らない。
