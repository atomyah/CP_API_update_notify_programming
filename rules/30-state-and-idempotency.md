# ルール: 状態管理と冪等性

## 保存先

SQLite 単一ファイル。テーブルは以下の4つ。

| テーブル | 役割 |
|---|---|
| `cursors` | ウォッチャーごとの前回実行位置（`watcher_id` が主キー） |
| `snapshots` | 差分検知用の前回値（`watcher_id`, `resource_id`, `item_id` で一意） |
| `notified` | 通知済みイベントの冪等キー（UNIQUE 制約で二重送信を防ぐ） |
| `dead_letter` | 送信に失敗し諦めたイベント（人が見る用。自動再送しない） |

## カーソルは機能ごとに分離する

`cursors` の主キーは `watcher_id`。ウォッチャー間でカーソルを共有しない。
これにより、1つのウォッチャーを停止・再開・巻き戻ししても他に影響しない。

## 失敗時はカーソルを進めない

- 1 サイクルの処理を SQLite のトランザクションで囲む。
- **イベントを 1 件でも処理しきれなかったら、そのサイクルではカーソルを前進させない。**
- 例外がウォッチャーの外に漏れないようにする。
  スケジューラは 1 つのウォッチャーの失敗をログに残して、他のウォッチャーの実行を続ける。
- 連続失敗が閾値（既定 5 回）を超えたら、そのウォッチャーを自動停止して警告を出す。
  壊れたまま回り続けて API 予算を食い潰す方が有害。

## 少なくとも1回配信 + 冪等除去

`datetime` は**秒精度で検索できる**（実測済み。`07-verification-results.md` 2章）。
当初「秒がないので分粒度が下限」と想定していたが、これは仕様書の記載が誤っていたためで、
実際は秒まで正確にフィルタされる。

それでもオーバーラップは必要。理由は秒精度の不足ではなく、次の2つが残るため。

- CP 側で `UPDATE_DATE` が確定してから検索結果に反映されるまでのラグ（大きさ不明）
- 同一秒に複数レコードが更新されうること

取りこぼしは通知漏れであり、重複通知より重い。よって次の方針を取る。

1. カーソルは「前回サイクルの開始時刻 − オーバーラップ幅」を使う。
   オーバーラップ幅の既定は **60 秒**（`date` 型でしか絞れない要件4のカーソルは **1 日**）。
2. 取得したイベントは必ず重複を含む。**冪等キーで除去してから通知する。**

カーソルは秒粒度（`yyyy-MM-dd HH:mm:ss`）で保存する。
検索条件に渡すときは CP の形式（`YYYY/MM/DD HH:MM:SS`）へ変換する。

### 冪等キー

```
(watcher_id, resource_id, event_type, payload_hash)
```

- `resource_id`: CP のリソース ID（例 `123_4`）
- `event_type`: `created` / `updated` / `completed` / `status_changed` など
- `payload_hash`: 通知本文を決定づける項目値を正規化して取った SHA-256

`notified` テーブルにこの 4 つ組で UNIQUE 制約を張り、
INSERT が成功したときだけ通知を送る。INSERT が競合したら既送信として黙って捨てる。

**通知送信より先に `notified` へ INSERT する。**送信後に INSERT すると、
送信成功・INSERT 失敗のときに二重送信する。逆順なら最悪 1 件落ちるだけで、
落ちたことは `dead_letter` で検出できる。

## ブートストラップ

初回起動時（カーソルが存在しないとき）は**スナップショットを作るだけで通知しない**。

差分検知は「前回値」があって初めて成立する。前回値がない状態で通知を出すと、
既存の全レコードが「変化した」と誤判定されて Slack が溢れる。

- 明示的に `--bootstrap` で起動したときのみスナップショットを構築する。
- ブートストラップ完了を `cursors` に記録し、以降の通常起動では通知を出す。
- ブートストラップ自体も流量予算に従う。全件走査になるので、
  完了までに複数サイクルかかることを許容する。

## スナップショットの寿命

`snapshots` は無限に増える。次のいずれかで刈る。

- 要件1（求職者項目）: 監視対象求職者に限定して保持する。対象外になったら削除。
- 要件4（対応履歴）: 走査窓（既定3日）を外れたら削除。
  ただし削除した ID が再び窓に入ると「新規」と誤判定するため、
  **削除は行わず `last_seen_at` で古いものを別テーブルに退避**する方が安全。
  PoC では削除せず、件数が問題になってから対処する。

## 時刻の扱い

- CP が返す `datetime` はタイムゾーン情報を持たない。JST として扱う。
- SQLite に保存する時刻は **JST の `yyyy-MM-dd HH:mm:ss` 文字列**で統一する。
  UTC 混在は差分検知のバグの温床になる。
- CP に渡す検索値は CP の形式（`yyyy/MM/dd HH:mm` または `yyyy/MM/dd`）に変換する。
  変換は 1 箇所（`core/timefmt.py` 想定）に閉じる。
