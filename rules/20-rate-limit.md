# ルール: 流量制御

## 大原則

**CP API への HTTP 呼び出しは、例外なく単一のトークンバケットを通す。**

仕様書「利用方法」に「1分間あたり240リクエストを超える場合、APIサービスを停止させて頂く可能性がございます」
と明記されている。停止されたら全要件が同時に死ぬ。これは性能上の都合ではなく可用性の問題として扱う。

## 実装上の不変条件

1. HTTP クライアントは `core/client.py` の 1 つだけ。
   ウォッチャーや通知モジュールから `requests` / `httpx` を直接呼ばない。
2. `core/client.py` は必ず `core/ratelimit.py` のトークンバケットから
   トークンを取得してからリクエストを送る。取得できるまでブロックする。
3. リトライもトークンを消費する。「リトライだから」と迂回させない。
4. アプリは**単一プロセス・単一トークンバケット**で動かす。
   機能ごとにプロセスを分けない。分けると合計流量が制御できなくなる。
   （複数プロセス構成が必要になったら、まず流量制御をどう共有するかを設計してから。）

## 予算

| 値 | 設定 |
|---|---|
| CP の上限 | 240 req/分（超えると停止リスク） |
| 平常時の上限 | **60 req/分**（上限の 25%） |
| バースト許容 | トークンバケット容量 20（瞬間的に 20 連続まで） |
| 緊急時の最大 | 120 req/分（上限の 50%）。設定変更でのみ到達可能とし、既定値にしない |

**240 が API キー単位か契約テナント単位かは仕様書に記載がない。**
テナント単位（他の連携と合算）である可能性を前提に、上記の余裕を必ず残す。
この点は CP ベンダーに確認する（`docs/design/06-open-questions.md`）。

## ウォッチャー側の責務

- 各ウォッチャーは 1 サイクルあたりの**リクエスト予算**を持つ。
  予算を使い切ったら処理を打ち切り、進捗（ページオフセット等）を保存して次サイクルに持ち越す。
  **打ち切ったサイクルではカーソルを前進させない。**
- 長時間ウォッチャー（要件4の更新検知など）は予算を小さなチャンクに分けて実行し、
  チャンクの合間に高優先ウォッチャー（要件2の進捗通知など）が割り込めるようにする。
- ウォッチャーは並行実行しない。スケジューラが 1 つずつ逐次に回す。
  並行化はトークンバケットの競合と可観測性の悪化に見合わない。

## 計測

- 1 分あたりの実リクエスト数を常にメトリクスとして記録する。
- 平常時上限（60/分）の 80% を 5 分継続で超えたら警告ログを出す。
- 起動から現在までの累積リクエスト数を、ウォッチャー別・エンドポイント別に集計できるようにする。
  予算見積り（`docs/design/03-rate-budget.md`）と実測が乖離したら設計を見直す。

## やってはいけないこと

- 検索の `limit` を小さくしてページ数を増やす（リクエスト数が増える）。常に 100 を指定する。
- 「念のため」の全件走査。走査範囲は必ず時刻・日付・ID の窓で有界にする。
- 通知の再送のためにイベントを再取得する。通知本文は最初の取得時に組み立てて保存する。
- パフォーマンステスト目的の連続リクエスト（仕様書で明示的に禁止されている）。
