# Phase 5 — 運用（トリガー本設定・日次サマリ・通し確認）

要件1〜3 を「動かしっぱなしにできる」状態にする。

## 目的

Phase3・Phase4 は手動実行で確認していた。**トリガーで自動運転**にし、
壊れたときに気づける状態を作る。GAS は手元 PC と違い常時動くので、
**Python 版で問題だった「断続起動」の制約がここで解消される。**

## 前提

- Phase4 完了
- 移植元: `app/main.py`（起動時チェック・ギャップ報告）、`app/core/scheduler.py` の自動停止
- 根拠: 仕様書 8.5 / 8.6 / 9.1 / 9.3 / 9.4節、9.5節（GAS では大部分が不要になる）

## 作るもの

| ファイル | 責務 |
|---|---|
| `src/setup.js` | `createTriggers()` / `deleteTriggers()`。**冪等に。二重登録しない** |
| `src/triggers.js` | `runDailySummary()` を追加 |
| `src/core/metrics.js` | 1分あたりのリクエスト数、ウォッチャー別・エンドポイント別の累積 |

## トリガー構成

| 関数 | 間隔 | 対応 |
|---|---|---|
| `runProgressFlow()` | 5分 | 要件2/3 |
| `runCareerStatus()` | 15分 | 要件1 |
| `runCareerAction()` | 15分 | 要件4（Phase6 完了後に有効化） |
| `runDailySummary()` | 日次 | 日次バッチ |

**⚠️ `createTriggers()` は必ず既存トリガーを削除してから作る。**
繰り返し実行すると同じトリガーが増殖し、流量が倍々になる。

## 日次サマリに出すもの

- 各ウォッチャーの実行回数・検知件数・通知件数
- 累積リクエスト数（予算見積り 5,000 req/日 との乖離。仕様書 8.1）
- 連続失敗して自動停止したウォッチャーの有無
- `dead_letter` の件数
- **担当者メール未設定でメールを送れなかった件数**（要件4。仕様書 3.3.6）
- `MailApp.getRemainingDailyQuota()` の残量（Phase6 完了後）

### 実環境確認の手順

```
1. clasp push
2. showTriggers()            今あるトリガーを確認（初回は空）
3. createTriggers()          3本作られる（要件4は enabled: false なので作られない）
4. showTriggers()            重複が無いこと。もう一度 createTriggers() しても増えないこと
   ここで1時間ほど放置する
5. runDailySummaryToday()    ops チャンネルへ届くこと。ピーク req/分 と実行回数を確認
6. showState()               カーソルが進んでいること
```

**⚠️ 止めたいときは `deleteTriggers()`。**画面から消すと管理外の状態が残る。

`runDailySummary()`（トリガーが呼ぶ方）は**前日ぶん**を集計する。
朝に走るので当日を集計してもほとんど空になるため。手で今日ぶんを見るときは
`runDailySummaryToday()`。

## Python 版との違い（記録しておく）

仕様書 9.5節（断続起動の扱い）は、手元 Windows PC で常時起動しない前提のもの。
**GAS では常時トリガーが回るため、9.5.2「停止期間中の中間の変化は失われる」
9.5.3「G > 3日 で要件4の日付変更を取りこぼす」9.5.4「再開時の通知洪水」は原則として起きなくなる。**
ただしトリガーの日次実行時間上限に当たれば止まるので、**止まったことを検知する仕組みは残す。**
